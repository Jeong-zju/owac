## Attempt-1 OOM root cause and RAM-retention repair

Attempt 1 exited native `1` at 18:36:05 after ~197 s and at least 10 recorded updates; rank 0 was SIGKILLed. The container cgroup quota is **116 GiB** even though host `free -h` reports 503 GiB. Worker RSS reached ~52 GB + ~44 GB before OOM (`memory.events oom=1`, `oom_kill=1`). Root cause: the training call site ignored `training.working_cache_sources` and constructed `AllBenchDataset` with the 256-source default RAW LRU; long RoboTwin episodes accumulated in RAM beyond quota. No math/history/data/global-batch change is involved.

Repair:
- config `training.working_cache_sources` is now wired into `AllBenchDataset(capacity=...)`; set to **16 native RAW sources per rank**.
- one-batch-ahead full CPU sample prefetch remains at 4 workers.
- teacher targets remain mmap/sliced, never preloaded.
- no RAM/VRAM/time/utilization abort threshold; only 380 GiB disk cap.
- first complete checkpoint saved at actual update 1, then 250-step/epoch checkpoints.
- failed attempt state is preserved; attempt 2 must start from the same initial student with seed/sampler 0, not resume the lost >=10 updates.

## Attempt 3 (r3) FD exhaustion root cause and repair

Attempt `train-r3` ended native exit 1 at 19:04:49 after ~423.31 s. Logs recorded ~300 updates; last full checkpoint is update 250. Root cause was not a new OOM: rank 1 hit `OSError 24 Too many open files` because `TargetStore` retained a persistent mmap per source across 1,923 random-locality sources. The RAW 16-source cache was not involved.

Final repair uses the simpler lifecycle: every `TargetStore.read` opens `np.load(..., mmap_mode="r")`, copies the requested row into an owned NumPy array, closes the mapping in `finally`, then constructs the tensor from the owned copy. No persistent target mmap cache, no LRU capacity, no locks, no FD leak; OS file/page cache supplies reuse and the small NPY header cost is negligible. Metadata JSON small cache remains. No dataset preload/hash/CRC/finite/resource gate is added; only the 380 GiB disk cap remains.

CPU tests cover 20 tiny shards read repeatedly and concurrently (4 workers), assert `/proc/self/fd` stays bounded and an old returned tensor stays valid. Logs/native error are preserved by Sol; the >50 updates beyond checkpoint 250 are not claimed as resumed. Manual resume uses complete optimizer/scheduler/RNG/sampler state at update 250.

## CPU/memory observation (2026-10-23)

Live sampling: each of two ranks had ~66 threads; `OMP_NUM_THREADS=8`, `MKL_NUM_THREADS=8`, `prefetch_workers=4/rank`, container CPU quota 32 cores. In a 20 s sample, two ranks used ~480 CPU-seconds and 117/200 periods were throttled. The same sample reported **8.2 GiB direct reclaim and 7968 major faults**; no new OOM was observed, but memory pressure cannot be ruled out as a contributing factor from this sample alone.

Facts and limits:

- Four CPU loader threads per rank and process-wide OMP/MKL pools are nested; the exact number of runnable CPU threads and kernel-level interaction was not instrumented. A `4 workers * 8 OMP` upper bound is possible, not measured.
- Two ranks against a 32-core quota makes oversubscription plausible, but throttling and reclaim together mean the bottleneck is not established as thread-only.
- Sol is running independent same-eight-sample CPU trials in separate processes. Warm trials were roughly 1.2-1.8 s with 8 threads and 1.9-2 s with 1 thread; this does **not** establish that fewer threads are faster. Worker count and thread-count changes are therefore not preset.
- Keep the existing `prefetch_workers=4/rank` until the independent measurements are available.
- A global `torch.set_num_threads(1)` in a worker would affect the whole process, including CPU-side work in the GPU-training process; whether that matters is unmeasured, not a confirmed training throttle.
- Do not change OMP/MKL, prefetch worker count, history, global16, loss, data split or validation frequency based on this observation alone.

If later measurements justify it, test process-level `OMP_NUM_THREADS`/`MKL_NUM_THREADS` and prefetch-worker combinations as scheduling experiments, without turning them into resource gates.
